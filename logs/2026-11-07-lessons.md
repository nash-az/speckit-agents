## Lessons
- **Run the Spec Kit commands for real, even from the operator session.** A session started in `~/private` does not
  load the repo's `/speckit-*` skills. The operator first followed each SKILL.md by hand, answered clarify itself, and
  used a reviewer agent as "analyze"; the person rejected that: running the commands is how the flow gets tested.
  What works: `claude -p --model claude-opus-5-5 --output-format json --permission-mode acceptEdits --allowedTools
  Read Grep Glob Edit "Bash(.specify/scripts/bash/*)" … -- "/speckit-clarify <context>" < /dev/null` with the repo as
  cwd, then `claude -p --resume <session_id> … -- "<answer>"` per question. No permission denials; about $0.2–0.3
  per clarify turn on Opus.
- **Pass `< /dev/null` to `claude -p`**, or it waits 3 s for stdin and warns.
- **Headless clarify checks the code and finds real gaps.** Its first question found that the draft's edge case
  ("refuse an early Stop") repeats the very failure the amendment fixes, because the supervisor deletes any leftover
  `control.json` at startup (`bin/sdd-supervise.py:627`). The hand-written draft had missed it.
- **Clarify does not know what the code already does unless told.** Its second question proposed a banner error that
  already exists (`bin/sdd-dashboard.py:3949`); a one-line operator note in the answer made it word FR-033 as only the
  new part. Plugin idea: the operator relay (or 006's automated clarify) passes code facts it finds along with answers.
- **Requirement ids collide across features.** 009's new FR-033/FR-034 share ids with 008's, and 009's "Effect on
  other features" names 008's. Spec Kit numbers per feature; nothing checks cross-feature references (ties to the
  2026-11-07 finding that analyze reads one feature only).
- **`/speckit-plan` on an amendment runs long**: 10 min 17 s, 67 turns, $4.46 on Opus, re-reading the large built
  feature before adding to it. It found four code gaps the hand-written plan missed (the launcher returns before the
  supervisor writes `status.json`; startup deletes any `control.json`; Stop now before any task suspends; no trace).
  Its one permission denial: a `cat >> research.md <<'EOF'` heredoc under acceptEdits; it fell back to Edit. Give
  headless Spec Kit commands Edit/Write and expect heredocs to be refused.
- **A plain backticked string becomes a "file" in the plan helper** (known, feedback `20261104-1710-1`): seen again
  in the hand-written tasks (`control.json`, `Cycle.run`, `subprocess.Popen`). Check the plan helper's `files` per
  task before a run.
- **The 1631 Stop bug was only half fixed by 009 T027/T028.** The operator's first read (the engine stops before any
  task, the banner has both buttons) concluded "only a test and a log are missing". `/speckit-plan`'s code reading
  found the start window still open: the launcher returns before the new supervisor writes `status.json`, so Stop is
  refused, and the supervisor deletes any `control.json` at startup. Check a "probably already fixed" conclusion
  against the whole path (launcher → status → controls → supervisor startup), not only the parts named in the report.
- **`/speckit-tasks` on an amendment**: 5.8 min, 39 turns, $2.90; 11 tasks (T034–T044) in Phases 16–21, each naming
  the existing tests it breaks (fake supervisor pids 4242/4343/4444 that a real `starting` status would make
  flaky; dashboard tests that list the state directory). Its own `python3 bin/sdd-tasks.py plan …` check was denied
  although `Bash(python3 bin/sdd-tasks.py *)` was allowed, most likely because it piped the output; the operator ran
  the check instead. Give headless commands a script that does the check in one plain call.
- **A headless Spec Kit command has no usage-limit protection.** The second `/speckit-plan` (after analyze) hit the
  weekly limit after 2.5 min and exited 1 with "You've hit your weekly limit"; it had written nothing, so it was run
  again from the start after the reset. The supervisor's 95 %/99 % rule covers only `/sdd-run`; a spec-cycle runner
  (006) needs the same pause, and should check the tree for half-written docs before a re-run.
- **A headless command can die on the network and lose its whole pass.** The second `/speckit-analyze` ran 17 min
  (48 turns, $3.03) and ended "API Error: Connection refused (ECONNREFUSED)" with no report; analyze is read-only, so
  nothing was half-written, but the work was lost. A spec-cycle runner (006) should retry a failed headless command
  once and keep the partial transcript.
- **Analyze pass 3 hit the 5-hour limit** after 6 min ($4.13) and returned only the limit text; re-run after the
  reset. Three of nine headless command runs in this amendment were lost (weekly limit, network, 5-hour limit): the
  spec flow needs the supervisor's usage pause and a retry as much as `/sdd-run` does.
- **Browser tests that skip during runs hide breakage.** Analyze pass 3 ran `tests.ui.test_banner` and found
  `WorkingJobBannerTest.test_working_job_names_the_job_and_offers_both_stops` failing on `main` ("Preparing Toy run" !=
  "Working on Toy run") since 009 T028 added `preparing`; the run's agents could not start a browser, so the UI
  tests skipped and the verifier approved. A run should report skipped test modules, and a `[manual]` browser pass
  should follow any UI change.
- **`claude -p --output-format json` returns only the last message.** Analyze pass 3 started the unit suite in the
  background, wrote its report, then a later turn reported only the suite result; the report was in the transcript
  (`~/.claude/projects/<repo slug>/<session>.jsonl`). Read the transcript, not just `result`.
- **Six analyze passes to a clean gate.** CRIT/HIGH/MED/LOW per pass: 1/3/5/9, 0/1/6/10, 0/2/3/4, 0/2/4/11, 0/1/5/12,
  0/0/2/9. About $90 of headless Opus runs for spec docs only (plan ~$2–4.5, tasks ~$2–3, analyze ~$4–8, clarify
  ~$0.5–1.4 per turn). Each pass reads the code deeper and finds a finer layer: design gaps, then behaviour
  mismatches and a failing browser test on `main`, then test wording against the harness (page-error check, test
  order, shared temp files). Plugin ideas: `/speckit-tasks` should check new tests against the test harness's rules,
  and a spec-cycle runner (006) should run the analyze → fix loop itself, with a cost cap and the person's questions
  queued in the dashboard.
