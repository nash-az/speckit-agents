How the dashboard should present a Spec Kit project

The current dashboard is a file browser with counters. The tools that do this well lead with what needs a person, then the live run, then the documents. This page covers what to keep, what the research found, and a clickable mockup of the proposed structure.

Fixed constraints

  • One project per dashboard. A plugin command (proposed name /speckit-agents:ui) starts the server and the UI on separate ports for the project it's run from. The plugin stores nothing, so there's no project picker.
  • Read-only. The dashboard never writes files or git. Answers, amendments and feedback go through a Claude Code session (research.md D9).
  • AI-free core (constitution VII). Everything it reports works with no model. Chat is an optional extra on the same backend.

What to keep, what to change

Keep (built and verified in 003 Phases 2–3)

  • sdd-tasks.py as the one parser for tasks, holds and BLOCKED.md, so the CLI and the dashboard can't disagree.
  • The status taxonomy: one key per status, with color, glyph and label, and statusBadge().
  • sdd-tasks.py events: run events derived from the engine journal, timestamped and costing no tokens.
  • Fixed-name /api/doc, active_feature(), run-id validation, the localhost-only Host check (421), and the never-writes test.
  • Sanitized markdown rendering with a table of contents and a raw toggle.
  • Polling every 3 s. It's proven, and the research doesn't argue for WebSockets at this scale.

Change (UI layer)

  • Drop the project dropdown and the "Load Project" button.
  • Replace the 14-item file-per-entry sidebar with views: Home, Features, Runs.
  • Replace the overview's six counters and duplicate file links with an inbox, the active run and feature progress.
  • Link things together: requirement → story → task → commit → agent log. Today every document is an island.
  • Show each attempt's verifier feedback inline. Today a rejection is only a count.
  • Move the UI out of a 1000-line string in a Python file into its own static files, served on its own port.

Proposed structure

Three views. Home answers "what needs me, and what's running". Features holds the documents, with progress and traceability. Runs goes from task to attempt to log. Chat is a drawer available from every view. Everything shown below is this project's real state, apart from one illustrative retry on the run screen.

Open decisions

  1. Server and UI split. I propose keeping the stdlib JSON API (sdd-dashboard.py, read-only) on one port, and plain HTML, CSS and JS files with no build step, served by a second stdlib static server on a second port. The UI calls the API with CORS limited to its own origin. A build step such as React and Vite would add a Node dependency to the plugin. My recommendation is no build step.
  2. Command name: /speckit-agents:ui. It prints both URLs and opens the UI.
  3. Traceability source. In 003, only 4 of 44 tasks name an FR directly. 34 cite a data-model section, and that section's heading names the FR. Commits carry (T###). That's enough for 003. Other projects may not write a data-model this way, so the tasks template could require each task to name its FR ids.
  4. One-click answers in the inbox need the action channel (contracts/action-channel.md). Until it exists, the inbox shows the question and the command to run.

Effect on the open 003 tasks

  • Unchanged: T021, T022, T024 (backend routes) and the skills tasks. The new views read the same API.
  • Rewrite: T026's UI part, which becomes the Runs view and the Home run card, built on the new UI files.
  • New tasks: split the UI into static files plus a second port; the /speckit-agents:ui skill; remove the project picker; the Home inbox; the Traceability view; doc cross-links.
  • Later features: amendment comments, one-click answers, steering a running agent, and chat (backlog 36 and 40, on the action channel).
